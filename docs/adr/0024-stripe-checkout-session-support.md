# ADR 0024: Add Stripe Checkout Session Support Alongside PaymentIntents

- Status: Accepted
- Date: 2026-08-18

## Context

ADR 0013 committed to Stripe Connect direct charges with PaymentIntents, confirmed client-side with Stripe.js Elements. That remains the right default for storefronts that want a fully custom checkout UI. Some storefronts instead want Stripe's own hosted checkout page (`checkout.stripe.com`), reached by redirecting the shopper's browser rather than embedding a payment form. Stripe models this as a distinct resource, the Checkout Session, with its own creation and retrieval endpoints, its own object id prefix (`cs_`), and its own webhook event family (`checkout.session.*`).

The existing `PaymentClientAction` contract assumed a single response shape: a PaymentIntent client secret for `stripe.confirmPayment()`. Its OpenAPI `type` field was a closed enum with one legal value, `confirm_payment`. Supporting a redirect-based flow needed either a second response shape or a widened one; introducing a second Store API resource and endpoint pair for what is, from the shopper's perspective, still "get me the next payment action" was not justified.

## Decision

Add a second `PaymentProvider` adapter, `stripe_checkout`, alongside the existing `stripe` adapter. Both talk to the same Stripe Connect account using the same direct-charge pattern (`Stripe-Account` header, same credential secret, same pinned API version); they differ only in which Stripe resource they create and how they report the resulting client action:

- `stripe` creates PaymentIntents (`POST v1/payment_intents`) and returns `PaymentClientAction { type: "confirm_payment", client_token: <PaymentIntent client secret> }`, unchanged from ADR 0013.
- `stripe_checkout` creates Checkout Sessions (`POST v1/checkout/sessions`, `mode=payment`, one aggregate order-total line item) and returns `PaymentClientAction { type: "redirect_to_checkout", client_token: <Checkout Session URL> }`. The storefront navigates the shopper's browser to that URL directly — `client_token` is repurposed to carry a URL for this `type`, rather than introducing a second field that would be unused by the other `type`.

A merchant selects the flow by configuring a `payment_provider_accounts` row with `provider = "stripe_checkout"` instead of `"stripe"` — the same mechanism already used to configure any provider account, requiring no new domain concept. `provider` was already a free-form string with no enum constraint.

`success_url`/`cancel_url` are supplied by the storefront when creating the Payment Attempt (`stripe_checkout` requires both; `stripe` ignores them). They are not persisted as new columns on `payment_attempts`: a Checkout Session is created exactly once, synchronously from the outbox worker's dispatch of the `payment.create_requested` event, so the URLs only need to survive that one hop. They travel through the outbox event's JSON payload, the same mechanism already carrying `provider`, `amount_minor`, and `currency` for every payment/refund outbox event. Storing them as columns would create state that is only ever read once and then stale forever, contradicting the intent of a persisted attribute.

Webhook verification stays unified under the existing `stripe` `PaymentWebhookVerifier` and the existing `POST /webhooks/v1/payments/stripe` endpoint. Stripe signs and delivers all webhook events for a Connect account, PaymentIntent or Checkout Session, to one endpoint/secret pair; splitting verification by adapter would require the merchant to configure and maintain two separate Stripe webhook endpoints and secrets for what is one underlying trust relationship. `map_stripe_event` gains new match arms for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `checkout.session.expired`, alongside the existing `payment_intent.*`/`refund.*` arms, feeding the same downstream `payment.authorized`/`payment.captured`/`payment.failed`/`payment.cancelled` event types the Payment Attempt state machine already understands. No new `PaymentAttemptStatus` variant, no new domain entity, no new `payment_attempts` column: `provider_reference` stores the Checkout Session id (`cs_...`) exactly as it stores a PaymentIntent id (`pi_...`) today, since nothing downstream inspects the prefix except the webhook mapper's own identifier validation.

Checkout Sessions have no separate authorization step — a fully paid session goes straight from nothing to `checkout.session.completed`. This maps onto the existing auto-authorize-then-capture shortcut that already exists for PaymentIntents whose `payment_intent.succeeded` event arrives while the Attempt is still `pending` (used when a provider's automatic capture skips a distinct authorization event). `checkout.session.completed` only triggers this when the event's `payment_status` is `paid` or `no_payment_required`; a `payment_status` of `unpaid` means an async payment method was selected and the checkout form was submitted, but funds have not settled — that case intentionally emits no state transition and waits for the `checkout.session.async_payment_succeeded`/`async_payment_failed` follow-up event.

## Consequences

- Stripe-specific wire types and authentication remain in infrastructure; the shared HTTP plumbing (credential resolution, form POST, authenticated GET) is factored into a small internal `StripeHttp` helper both adapters hold, avoiding duplicated request/response handling between the two adapters.
- `PaymentClientAction.kind`/OpenAPI `type` now has two legal values with different meanings for `client_token`. Callers must branch on `type` before deciding what to do with `client_token` — treat it as a client secret for `confirm_payment`, or as a navigation target for `redirect_to_checkout`.
- `success_url`/`cancel_url` are shopper-browser-supplied redirect targets. The API layer requires `https://` and requires both-or-neither, but does not validate that the URLs' origin matches the calling Store's own domain. A storefront that lets an unauthenticated caller control these values arbitrarily creates an open-redirect surface through Stripe's hosted page. Full server-side validation against the Store's own domain was deliberately deferred as a follow-up rather than included here — storefronts should pass only their own trusted origin. *Editorial note (2026-08-18): the Store-owned Custom Domains feature this follow-up would have validated against was removed as over-engineered for the project's actual deployment model (each Store runs its own storefront instance with its own publishable key); this follow-up is abandoned rather than pending.*
- Two Stripe-backed provider accounts can be configured per Store (one `stripe`, one `stripe_checkout`) since `payment_provider_accounts` allows one row per distinct `provider` value; each goes through the same onboarding readiness check against the same underlying Connect account (`stripe_account_readiness`, shared between both adapters' `PaymentProviderOnboarding` implementations).
